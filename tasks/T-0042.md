# T-0042 Gallery thumbnail follow-up covers batches larger than one page
Issue: #90
Request: #65
Origin: T-0036
Status: review

## Goal
T-0036 (PR #89) follows up on new uploads' thumbnails by fetching the gallery's first page (`limit=120`) a bounded number of times (`lib/mediaThumbnailFollowUp.ts`, wired in `useRefreshMediaAfterUploads` in `hooks/useMedia.ts`). A batch of more than 120 uploads from the media gallery is only partly followed: uploads beyond the first page never get their thumbnail copied in, even when their tiles are loaded, and keep the follow-up running for its full bound (~55 s); and uploaded items not loaded when the batch refresh landed are dropped from the followed set by `pathsAwaitingThumbnail`, so tiles the user scrolls into later keep the placeholder until a focus refetch or reload. Found in code review of T-0036, round 1, finding C1.

Suggested fix: size the follow-up request to the followed count (up to the backend's 200 max), and keep not-yet-loaded paths in the followed set, dropping a path only once its item is loaded with a thumbnail, it is gone, or the bound ends.

## Acceptance criteria
1. After a batch of more than 120 uploads from the media gallery, every loaded uploaded tile, including ones loaded by scrolling during the follow-up window, shows its thumbnail within a few seconds of it being generated, with no reload or tab switch.
2. The follow-up stays bounded (same time limit) and stops early once every followed item has a thumbnail; items that never get one do not cause endless polling.
3. T-0033's one refetch per batch and the T-0029/T-0031 paging behaviour are unchanged.
4. Tests cover a batch larger than one page and an uploaded item loaded after the batch refresh. Build, typecheck and tests pass.

### 2026-11-22 — Engineering — PR #99 opened
- PR: https://github.com/gustavoiha/file-storage/pull/99 (branch `agent/T-0042-thumbnail-followup-pages`, rebased on main at b433bae).
- `lib/mediaThumbnailFollowUp.ts`:
  - Each round requests the newest items in pages sized to the batch (min the gallery's 120, max the API's 200). The size is set at `start` and does not shrink as paths drop.
  - The round walks on by cursor only while a followed upload is unseen, at most one page more than the batch needs.
  - `fetchLatest` is replaced by `fetchPage({ cursor?, limit })`, with a new `minPageSize` option.
- `pathsAwaitingThumbnail` is replaced by `pathsStillFollowed`, which keeps uploads that are not loaded. A path is dropped when one of these happens:
  - it is loaded with a thumbnail, or a written round returned it with one;
  - it is not listed where the newest items are (a full walk did not find it, a walk passed its `updatedAt`, or the fully loaded gallery lacks it);
  - the same 13-round bound runs out.
- An in-flight round that a new batch restarted does not drop paths it did not see.
- `useRefreshMediaAfterUploads`: wires `fetchPage` to `listMedia` and passes `minPageSize: MEDIA_PAGE_SIZE`. The single invalidation per batch and the gallery paging are unchanged.
- Tests:
  - lib: 250-upload batch (two pages of 200), 130-upload batch (one request of 130), an upload loaded by scrolling, early stop, bound with an unloaded upload that never gets one, a trashed upload in a long listing, a never-found upload, the restart race (checked to fail without the guard);
  - hook: 130 uploads through the dialog plus `fetchNextPage`, every tile gets its thumbnail, then it stops with one invalidation.
- typecheck, test and build pass. Status review.
