# T-0018 Trash page handles two trashed items with the same path separately
Issue: #39
Request: #5
Origin: T-0013
Status: review

## Goal
On the trash page, the same file path can be in the trash more than once (a file trashed, re-created, trashed again). The page tracks the pending purge and restore by path (`pendingSecondaryActionPath`, `purgeFilePath` and `pendingRestorePath` in `apps/web/src/pages/TrashPage.tsx`), and the purge and restore API calls take only the path. While testing T-0013, purging one copy set both rows to "Purging..." and once left the Purge dialog open until a reload. Make each trashed item act on its own.

## Acceptance criteria
1. With two trashed items that share a path, starting Purge now or Restore on one row shows the pending label only on that row.
2. Purge now and Restore act on the item the user picked, and the result is defined and tested in the backend (which copy is purged or restored, what happens to the other one); no request silently acts on both or on the wrong one.
3. After a successful purge, the dialog closes and the trash list shows the remaining copy; after a failure, the dialog shows the error and can be closed.
4. Rows with the same path have distinct React keys and accessible names that tell them apart (e.g. the trashed date).
5. Unit tests cover the duplicate-path case in the trash page and in the backend purge/restore handlers. Build, typecheck and tests pass.

- Backend: `listTrash` returns `fileNodeId`; purge and restore take an optional `fileNodeId` (`lib/trashedFileTarget.ts`). With it they act only on that file node while it is trashed at the given path (else 404). Without it they act on the single trashed file at the path, and return 409 with no change when several trashed files share it. Restoring the second copy after the first is back still hits the existing name-conflict 409.
- Frontend: rows, React keys, pending labels and purge/restore requests use the file node id; rows show "Trashed <date, time>" and buttons are named with path and trashed time; purge dialog shows the trashed time, closes on success, shows the error and can close on failure; restore errors are now shown.
- Tests added for the duplicate-path case in both handlers, `listTrash`, `TrashPage`, `FileList` and the hooks. typecheck, test and build pass. Status review.

## Security review (round 1)
PR #41. No findings.
- Auth: purge, restore and list trash routes are unchanged; each handler still calls `requireEntitledUser` and takes `userId` from the token only.
- New `fileNodeId` input: zod-validated (trimmed, 1-200 chars, optional). `resolveTrashedFileTarget` looks it up with `getFileNodeById`, a DynamoDB GetItem on `PK = buildFilePk(token userId, dockspaceId)`, `SK = L#<fileNodeId>`. Any value the client sends stays inside the caller's own partition and can only match a file node (`L#` prefix). That node must also be in TRASH and trashed at the given path, or the request gets a 404. So an id from another user or dockspace, or an active or purged file, cannot be purged or restored (no IDOR). The S3 key that gets purged or restored still comes from the stored node (`s3Key`), never from the request.
- Path-only requests with several matches get a 409 with a fixed message and change nothing. Responses add only the caller's own `fileNodeId`.
- Frontend: the restore error is shown as React text through `Alert`. There is no raw HTML, the new date formatter uses `Intl`, and nothing new goes to storage, logs or URLs.
- No infra, IAM, CORS or dependency changes.
