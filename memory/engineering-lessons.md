# Engineering lessons (owned by Engineering agent)
Implementation details repeatedly flagged by the testing or code-review agents. Each entry: rule, why, times flagged, tasks.

- Touch press-and-hold: after a hold fires, handle every event the release can produce (touchend, compat mousedown/focus, click, Android contextmenu). Any "swallow the next X" flag must be cleared on every path where X will not come (cancelled touchend, menu closed), or it eats the next keyboard or assistive-tech activation. Test the release AND the next keyboard activation. Flagged 2x: T-0005 test rounds 1 and 2.
- Focus indicators drawn in CSS: use `:focus-visible` (a container: `:has(:focus-visible)`), never `:focus` or `:focus-within`, because the app moves focus with `.focus()` after mouse actions (dialog close, Move to Trash) and mouse users then see a stray ring. Keep reveal-only styles (actions trigger, checkbox) on `:focus-within` so they stay reachable. Put a `:has()` selector alone in its rule and add an `@supports not selector(:has(*))` `:focus-within` fallback. Check both paths in headless Chromium: a mouse click that moves focus, and the same move after keyboard input. A state rule (`[aria-current]`, `--selected`, `--previewed`) that sets `box-shadow`/`background`/`outline` at the same specificity and comes after the `:focus-visible` rule replaces the ring: add a combined `<state>:focus-visible` rule after it, and Tab onto a row in that state when checking. Flagged 3x: T-0010, T-0013, T-0017.
- State updated from a mutation response AND recomputed from a query the mutation invalidates: never apply both to the same item. Pick one source per item (e.g. skip the delta for the open folder, whose listing refetches), because the order in which the response and the refetch land is not fixed (on the live site the refetch usually wins). In tests, a hook mock with a fixed cached result never refetches and hides this: make the mock able to replace the data and re-render its users, and test both arrival orders, for every action that takes this path (restore AND purge, not just one of them). Flagged 3x: T-0016 code review C1 and test round 1, T-0021 code review C1 (purge had only the refetch-first order).
- A control that removes itself or its container (Dismiss, Close, Cancel, a row action that drops the row) must move focus to a stable related control first (the row's main action, the dialog's opener), never leave it to fall to `<body>`. For a row removed after an async success (restore, purge, trash), move focus to the next row's main action, else the previous row's, else a `tabIndex={-1}` list/empty-message fallback with a `:focus-visible` ring; do it only if focus fell to `<body>`, and for a dialog-confirmed action only once the dialog has closed. Any async action that disables its own button (dialog submit, inline row action like Restore) leaves focus on body when it fails: put it back (a dialog control such as Cancel via `useFocusAfterFailedSubmit`; for a flat-list row, the row's action button via `FileList`'s `focusAfterFailure`), only if focus is still on body; and an opener re-rendered while the dialog was open (pending row) must be found again by its row path, not kept as a stale element. Test `document.activeElement` after the click, not only that the control is gone. When a component has several variants (desktop/phone) or entry points (create from the strip vs. from a full-screen list), each path that moves focus needs its own focus test, even when it looks like the one you already tested (T-0026 code review C1: the phone create flow). This includes Try again / Retry buttons inside an error state: never let the click swap the error block for a loading state; keep the same button mounted and marked busy (`aria-disabled`, not `disabled`) until the request settles, so a failed retry keeps focus on it, and when success replaces it, move focus to the container's stable control (Close/Back) if it fell to `<body>` — and list every state success can lead to (the content, a not-found message, a 403 notice): each one without a control still needs a `tabIndex={-1}` fallback such as the page title (`Page`'s `titleRef`), with a test per state (T-0028 code review C1) (React Query v5 clears `error` while a query with no data refetches, and ANY refetch does it, not only your retry: an invalidation after an upload or create, a `fetchQuery` from discovery. So keep the last failure and its message yourself until data loads or the key changes, and keep the error mounted through every refetch. Tracking only the Try again retry was not enough: T-0025). Before writing any conditional render that can hold the focused element, ask what happens to focus when the condition flips. That includes conditions you do not own: never put an error with Try again in a slot another component hides on its own (e.g. a list's empty slot, which goes away when a pending create/upload row appears); render it where only its own error state decides, e.g. above the list. jsdom does not blur a button when it becomes disabled, so focus tests for a failed action pass without the fix: simulate the browser (a `MutationObserver` on `disabled` that briefly re-enables the focused button and calls `blur()`, as in `TrashPage.test.tsx`) and assert focus is on body mid-request. In a virtualized list, a focus target picked by index (the first new tile, the last tile) may not be rendered: the user can scroll while the request runs, so always end the chain with an element that is always mounted (the scroll box with `tabIndex={-1}`), and test the scrolled-away case (T-0029 code review C2). A close fired from `mousedown` on something that cannot take focus (a backdrop, the empty area of a full-screen viewer) must call `preventDefault()`: the press's default action blurs the element you just focused and focus lands on `<body>` (T-0032, seen in Chromium; jsdom does not do this, so make the test's mouse-press helper blur unless the default was prevented). Flagged 12x: T-0009 (dialogs), T-0019 code review C1 (row error Dismiss), T-0021 (trash restore/purge), T-0022 (failed purge / folder trash), T-0015 test round 2 (folder info Try again), T-0023 (failed inline restore), T-0024 code review C1 (failed-listing Try again in the list's empty slot), T-0025 (background refetch removed the failed listing's Try again), T-0026 code review C1 (no test for the phone create flow's focus return), T-0028 code review C1 (successful retry into "not found" / 403 left focus on body), T-0029 code review C2 (neither tile rendered after a successful gallery Try again), T-0029 test round 1 finding 2 -> T-0032 (closing the gallery preview left focus on body; return it to the last shown item's tile, scrolled into view if virtualized).
- Every modal surface (`aria-modal="true"`: dialogs, full-screen viewers, sheets) takes focus when it opens (`autoFocus` on its safest control, e.g. Cancel or Close) and traps Tab with `useDialogTabTrap` on its root. Do it when you add the surface, not when testing finds Tab walking the page behind it. Keep `useDialogDismiss`'s tabbable selector in step with what the surface can hold (it now includes media with `controls` and `iframe`). An element focusable in the browser but missing from that list counts as outside the dialog, so the trap jumps to the first control. Flagged 2x: T-0020 (confirmation dialogs), T-0035 (gallery preview, found in T-0032 test round 1).
