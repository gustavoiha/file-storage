# T-0029 Gallery infinite scroll: no jump on phone, load further ahead on desktop
Issue: #66
Request: #65
Status: review

## Goal
The media gallery (`apps/web/src/pages/dockspaceMedia/VirtualizedMediaGrid.tsx`) loads 60 items per page (`useMediaFiles` in `apps/web/src/hooks/useMedia.ts`) and only asks for the next page when less than 2 rows are left below the viewport. The human reports that on phones the scroll jumps when the next images start loading, and that on desktop they must scroll to the bottom, wait, and repeat. The gallery should keep its scroll position steady while pages append, and load far enough ahead (more at once, and further ahead when the user scrolls fast) that normal scrolling rarely reaches an unloaded bottom.

Notes for engineering: on phone (<= 920px) the grid is a fixed-height inner scroll box (`height: min(68vh, 760px)`, `overscroll-behavior: contain`) inside a page that also scrolls, and "Loading more media..." is appended inside the scroll box; both are suspects for the jump, as are viewport height changes from the mobile browser bar (68vh) feeding the ResizeObserver. Find the real cause before fixing. Also check that a failed next-page request does not retrigger in a loop: the load-more effect reruns when `isFetchingNextPage` goes back to false while `hasNextPage` stays true. Layout changes to the gallery (card frame, sidebar, gapless grid) are T-0030; keep this task to loading and scroll behaviour.

## Acceptance criteria
1. Phone (375x812, touch emulation) on All media with at least 4 pages of media: while scrolling down through at least 3 page loads, appending a page never moves the content on screen: the top visible tile keeps its on-screen position (within 1px) and the scroll position is not reset or shifted by the append, by the loading indicator, or by a viewport height change from the browser bar.
2. The loading indicator does not change the layout of the loaded tiles (reserved space or overlay), and it is announced politely (`role="status"` or equivalent) only while loading.
3. Desktop (1440x900): the next page is requested when the loaded content left below the viewport is less than a lookahead of at least 2 viewport heights (not 2 rows), and the page size is larger than 60 (within the backend max of 200). After a page lands, if the remaining content is still under the lookahead, the next page is requested right away without waiting for another scroll event.
4. The lookahead grows with scroll speed: when the user scrolls fast, the gallery requests further ahead (a bounded maximum, e.g. 6 viewport heights) so a continuous fast scroll reaches an unloaded bottom less often. The threshold rule is a pure function with unit tests for slow, fast and stopped scrolling.
5. Bounded requests: at most one next-page request in flight; no request when there is no next page; when a next-page request fails, automatic loading stops (no request loop), an error with Try again is shown at the end of the grid, Try again sends one request per press, and on success automatic loading resumes. The already loaded tiles stay visible during the error.
6. Unchanged: album views (not paginated), grid size toggle, multi-select (including shift-range), preview with previous/next, keyboard access to tiles, and the first-page loading and empty states.
7. Unit tests cover the threshold function, the chained fetch after a page lands, and the failed next-page path. Build, typecheck and tests pass.

### 2026-11-22 — Engineering — PR opened: row-gap root cause fixed, lookahead loading, bounded retries
- PR: https://github.com/gustavoiha/file-storage/pull/68 (branch `agent/T-0029-gallery-infinite-scroll`).
- Root cause, measured in headless Chromium at 375x812 with touch, using the real grid and CSS and a fake paginated query: the virtual grid placed rows every `rowHeightPx` while the `<ul>` kept the CSS `gap: 0.7rem`. So every tile moved 11.2px each time a row left the top of the rendered window: a visible jump in WebKit (no scroll anchoring), and a silent ~12px `scrollTop` correction in Chrome. The old 2-row trigger fired at a row boundary, so the jump came with the load.
- Ruled out: `68vh` is the static viewport unit, so the browser bar does not resize the box. `viewportHeight` only moves the bottom of the render window, never the top spacer.
- After the fix: 0 tile shifts, with and without scroll anchoring, on phone and desktop across 6-20 appends.
- Fix:
  - Rows sit on a stride of `rowHeightPx + MEDIA_GRID_GAP_PX`, and that gap is set inline on the list.
  - Loading text is in a reserved footer (`role="status"`).
  - Pages of 120 items (`MEDIA_PAGE_SIZE`).
  - Lookahead is 2 viewport heights plus 1.5s at the current scroll speed, capped at 6 (pure functions in `mediaGridLoadAhead.ts`). A viewport height is the taller of the scroll box and the window.
  - Fetches chain after a page lands.
  - `cancelRefetch: false`, so at most one request is in flight.
  - A failed next page stops automatic loading and shows Try again at the end of the grid (not the top alert). The failure is remembered through background refetches.
  - Try again sends one request per press, stays mounted and busy while it runs, and on success moves focus to the first new tile.
- Tests: `mediaGridLoadAhead.test.ts` (pure functions) and `DockspaceMediaPaging.test.tsx`, which uses real React Query to cover chaining, one request in flight, the failure path with focus, the status region, and the row layout. Typecheck, tests and build pass.
- For T-0030: if the grid becomes gapless, change `MEDIA_GRID_GAP_PX`; the virtual math follows it.

## Security review (round 1)
PR #68, reviewed 2026-11-22. Frontend only (`apps/web`); no backend, infra or dependency changes.

No findings.

Checked:
- Page size 120: `listMedia` in `packages/backend/src/handlers/listMedia.ts` is unchanged. It still requires an entitled Cognito user (`requireEntitledUser`), checks that the caller owns the dockspace (`ensureMediaDockspace(userId, dockspaceId)`), and clamps `limit` to `MAX_LIMIT = 200` on the server. The client value cannot raise the cap.
- Request volume: `shouldLoadNextPage` stops when there is no next page, while a fetch is in flight, or after a next-page error. `fetchNextPage({ cancelRefetch: false })` joins a fetch that is already in flight. Chaining stops once the loaded content reaches the lookahead, which is capped at 6 viewport heights. Try again does nothing while a fetch is running. So a failure cannot start a request loop.
- Rendering: the next-page error message (`mediaQuery.error.message`) is rendered as JSX text, so React escapes it. There is no `dangerouslySetInnerHTML`. The focus `querySelector` uses `data-media-index` with numeric indexes only, so no data reaches the selector.
- No secrets, tokens, logging or storage changes. No new packages.
