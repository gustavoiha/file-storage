# T-0035 Gallery preview takes focus when it opens and keeps Tab inside
Issue: #77
Request: #65
Origin: T-0032
Status: deploying

## Goal
When the media gallery's full-screen preview opens, keyboard focus stays on the tile behind the overlay. The preview is `aria-modal="true"`, but Tab first walks 6 hidden controls (the next tiles, Find duplicates, Trash, Detailed usage, All media) before it reaches Close preview and Next/Previous, and a screen reader user gets no announcement of the dialog. Already on main: `apps/web/src/components/files/FileViewerDialog.tsx` (variant `media-fullscreen`, used by `DockspaceMediaPage`) has no focus move on open and no focus trap. Found while testing T-0032 (#70), round 1, finding 1.

Notes: follow the confirmation dialogs' pattern from T-0020 (focus on open, document-level Tab trap). Keep T-0032's focus return on close (focus goes back to the tile of the item shown last before the preview unmounts). T-0030 changes the same gallery files; rebase on main before opening or updating the PR.

## Acceptance criteria
1. Opening the preview (Enter on a tile, or a click/tap) moves focus into the dialog (for example to Close preview), and the dialog is announced with its accessible name.
2. While the preview is open, Tab and Shift+Tab stay inside its controls (Close preview, Previous, Next, any other preview controls); the gallery behind it cannot be reached.
3. Escape, arrow keys, Previous/Next and every close path keep working, and T-0032's focus return on close (to the tile of the item shown last, `:focus-visible` only for keyboard users) is unchanged.
4. Mouse/touch opening does not show a focus ring inside the preview unless the user then uses the keyboard (`:focus-visible` only).
5. Unit tests cover focus on open, the Tab/Shift+Tab trap and the unchanged focus return; no new axe violations on desktop and phone. Build, typecheck and tests pass.

## Code review (round 1)
PR #80 at 29a3a45 (on top of main 9c3fc64). Checked: autoFocus on Close preview (the dialog mounts only when open, so it fires on every open; React focuses it at commit, before effects), `useDialogTabTrap` on the `<dialog>`, the nav-disabled focus move (handles both browsers that blur a disabled button and ones that keep it as `activeElement`; both-ends case falls back to Close), the shared tabbable selector change (only `trapTabKey` uses it; no other trapped dialog holds media or an iframe), and that T-0032's focus return still runs before the preview unmounts (`onClosePreview` focuses the tile synchronously). Tests cover focus on open (keyboard and click), the Tab/Shift+Tab trap, disabled Previous, Tab from body, both nav-disabled moves and focus return after tabbing.

- **C1 (non-blocking, suggest fixing here):** `apps/web/src/components/files/FileViewerDialog.tsx` L76-96 with `FilePreviewContent.tsx` L101-105 / L141-157. Focus in the preview content falls to `<body>` when the item changes. The trap now deliberately lets Tab reach the video/audio controls (and the "Open file in a new tab" link of an over-limit or unsupported file). With focus there, ArrowLeft/ArrowRight (or a swipe) switches the item. The new file's download-session query is pending, so `FilePreviewContent` swaps to the thumbnail placeholder, the focused element unmounts, and focus lands on `<body>` inside the `aria-modal` dialog. A screen-reader user loses their place until the next Tab, which the trap sends to Close. The nav-disabled effect only handles the nav buttons. This is the "what happens to focus when the condition flips" rule in engineering-lessons. Fix: when the shown file changes while the preview is open and `focusIsLost()`, focus Close preview (for example, extend the existing effect to depend on `file?.fileNodeId`). Add a test where the mocked content renders the video only for one item, focus the video, press ArrowRight, and assert focus is on Close. It was partly reachable before this PR (Tab walked to the video after the hidden page controls), but this task is about focus inside the preview.
- **C2 (non-blocking, pre-existing, follow-up):** `apps/web/src/components/files/FileViewerDialog.tsx` L83-96. The document-level ArrowLeft/ArrowRight handler calls `preventDefault()` and navigates even when the event target is a `<video controls>`/`<audio controls>`. That suppresses the native seek done by the media's default key handling, so keyboard users who Tab to the video (now an intended stop in the trap) cannot seek with the arrow keys, and each press changes the item instead (which then triggers C1). Fix: skip gallery navigation when `event.target` is (or is inside) an `audio`, `video`, `input`, `textarea`, `select` or `iframe`, and leave Previous/Next and arrows from the other controls as they are. Not caused by this PR, so it can be its own task.
