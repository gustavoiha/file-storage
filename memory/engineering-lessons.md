# Engineering lessons (owned by Engineering agent)
Implementation details repeatedly flagged by the testing or code-review agents. Each entry: rule, why, times flagged, tasks.

- Touch press-and-hold: after a hold fires, handle every event the release can produce (touchend, compat mousedown/focus, click, Android contextmenu). Any "swallow the next X" flag must be cleared on every path where X will not come (cancelled touchend, menu closed), or it eats the next keyboard or assistive-tech activation. Test the release AND the next keyboard activation. Flagged 2x: T-0005 test rounds 1 and 2.
- Focus indicators drawn in CSS: use `:focus-visible` (a container: `:has(:focus-visible)`), never `:focus` or `:focus-within`, because the app moves focus with `.focus()` after mouse actions (dialog close, Move to Trash) and mouse users then see a stray ring. Keep reveal-only styles (actions trigger, checkbox) on `:focus-within` so they stay reachable. Put a `:has()` selector alone in its rule and add an `@supports not selector(:has(*))` `:focus-within` fallback. Check both paths in headless Chromium: a mouse click that moves focus, and the same move after keyboard input. A state rule (`[aria-current]`, `--selected`, `--previewed`) that sets `box-shadow`/`background`/`outline` at the same specificity and comes after the `:focus-visible` rule replaces the ring: add a combined `<state>:focus-visible` rule after it, and Tab onto a row in that state when checking. Flagged 3x: T-0010, T-0013, T-0017.
- State updated from a mutation response AND recomputed from a query the mutation invalidates: never apply both to the same item. Pick one source per item (e.g. skip the delta for the open folder, whose listing refetches), because the order in which the response and the refetch land is not fixed (on the live site the refetch usually wins). In tests, a hook mock with a fixed cached result never refetches and hides this: make the mock able to replace the data and re-render its users, and test both arrival orders, for every action that takes this path (restore AND purge, not just one of them). Flagged 3x: T-0016 code review C1 and test round 1, T-0021 code review C1 (purge had only the refetch-first order).
- A control that removes itself or its container (Dismiss, Close, Cancel, a row action that drops the row) must move focus to a stable related control first (the row's main action, the dialog's opener), never leave it to fall to `<body>`. For a row removed after an async success (restore, purge, trash), move focus to the next row's main action, else the previous row's, else a `tabIndex={-1}` list/empty-message fallback with a `:focus-visible` ring; do it only if focus fell to `<body>`, and for a dialog-confirmed action only once the dialog has closed. Test `document.activeElement` after the click, not only that the control is gone. Flagged 3x: T-0009 (dialogs), T-0019 code review C1 (row error Dismiss), T-0021 (trash restore/purge).
