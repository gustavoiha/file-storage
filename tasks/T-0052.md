# T-0052 Menu items use one focus ring style in every menu
Issue: #111
Request: #65
Origin: T-0051
Status: testing

## Goal
Menu items should show one app focus ring style in every menu. Today the shared `DropdownMenu` items (`.dropdown-menu__item` in `apps/web/src/components/ui/DropdownMenu.tsx`: files page Upload, Dockspace / Folder options, row Actions, Account) have no `:focus-visible` rule in `apps/web/src/styles/layout.css`, so they show the browser default outline (thin, orange under phone emulation), while New dockspace (`.dockspace-switcher__create-menu-item`), Gallery options (`.gallery-options-menu__item`) and the album menu (`.gallery-album-menu__item`) show the app's 2px solid ring. Since T-0051 keyboard-opened menus focus their first item, so the difference is more visible. Found while testing T-0051 (#109), round 1, finding 1 (pre-existing on main).

## Acceptance criteria
1. Every `DropdownMenu` item (including the row right-click / long-press menus) shows the same app focus ring as the gallery menu items when focused from the keyboard, on desktop and phone, with no browser default outline.
2. The ring stays keyboard-only (`:focus-visible`); mouse hover and tap show no ring.
3. The ring is not clipped by the menu's edges or scroll area, and menu sizes and item spacing do not change.
4. Checked on the files page Upload menu (desktop and the phone floating button), Dockspace options, a row Actions menu, Account, New dockspace, Gallery options and the album menu. Build, typecheck and tests pass.

## Code review (round 1)
- PR #114 reviewed (commit ef37e69: `apps/web/src/styles/layout.css`, new `apps/web/src/tests/styles/dropdownMenuItemFocus.test.ts`). Checked that every menu in the criteria renders its items through `DropdownMenu.Button` / `RadioItem` / `Link`, which always add `.dropdown-menu__item`: files page Upload and Dockspace / Folder options (`DockspaceFilesHeaderActions`), row Actions and the right-click / long-press menus (`FileList`), Account (`TopNav`), New dockspace (`DockspaceSwitcher`), Gallery options and the album menu. So the one shared rule reaches all of them. No `outline: none` or later outline rule in `layout.css` targets a menu item class and overrides it, and no state rule (`[aria-checked]`, `[aria-disabled]`, `:hover`) sets `outline` or `box-shadow`. The ring is keyboard-only (`:focus-visible`), drawn inside the item (offset -2px) so the scrolling album list cannot clip it, and an outline takes no layout space. A real outline also shows in forced colors. The guard test reads the real CSS and would catch a removed shared rule, a per-menu outline override, a `:focus` / `:focus-within` ring, or a size change in a focus rule.
- C1 (non-blocking): `apps/web/src/styles/layout.css` lines 159-163 (`.top-nav__account-item:hover, .top-nav__account-item:focus-visible`) and 258-261 (`.dockspace-switcher__create-menu-item:hover, ...:focus-visible`) also give a keyboard-focused Account or New dockspace item a `--bg-soft` fill. The other five menus show only the ring on keyboard focus; their fill is on `:hover` only. The ring itself now matches everywhere, which is what criterion 1 asks for, so this is a small leftover difference in focus style, and it was there before this PR. Fix if wanted: drop the `:focus-visible` selector from those two rules, so focus is the ring alone in every menu, the same as Upload, Options, Actions and the gallery menus.

## Review decisions (round 1)
- C1 (Account and New dockspace items also get a `--bg-soft` fill on keyboard focus): discard. Confirmed in `layout.css` (lines 159-163 and 258-261 on the PR head), but it was there before this PR. The fill is an extra focus cue, not a defect, and a tint on focus is already an accepted pattern (design preferences: gallery tiles show tint plus inset ring on focus). Changing it is a matter of taste.
