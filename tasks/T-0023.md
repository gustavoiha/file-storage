# T-0023 Trash page keeps focus on the row after a failed restore
Issue: #50
Request: #5
Origin: T-0021
Status: new

## Goal
On the trash page (`apps/web/src/pages/TrashPage.tsx`, flat `FileList`), after a failed Restore, keyboard focus is on `body`: while the request runs the row's Restore button is disabled ("Restoring..."), the browser blurs it, and nothing puts focus back when the per-row error appears. The next Tab starts from the top of the page. Focus should stay with the row that failed.

## Acceptance criteria
1. After a failed Restore, if focus fell to `body` during the request, it moves to that row's Restore button (or the row's error Dismiss button), with a visible focus ring for keyboard users. Never `body`.
2. If the user moved focus elsewhere during the request, it is left where it is.
3. The per-row restore error (T-0019) is still announced, and Dismiss still returns focus to the row's Restore button. Successful restores keep T-0021's focus handling.
4. A unit test covers focus after a failed restore in a way that reproduces the blur of the disabled button (jsdom does not blur disabled elements, so the test must simulate it). Build, typecheck and tests pass.

## Notes
- Pre-existing on main (`disabled={isActionPending}` on the Restore button in `FileList.tsx`); not caused by T-0021 (PR #49). Builds on T-0021's focus-after-removal code in the flat `FileList`, so start after PR #49 is merged.
- The same symptom inside the Purge dialog after a failed purge is already covered by T-0022 (#48); keep this task to the inline Restore.
