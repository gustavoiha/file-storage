# T-0012 Keep focus in the file list after a file is moved to the trash
Issue: #28
Request: #5
Status: deploying
Origin: T-0011

## Goal
After a file is moved to the trash from its row menu with the keyboard, focus falls to the page body because the row (and the menu) is removed. Keyboard and screen reader users lose their place, and the next Tab starts from the top of the page. The folder trash dialog already returns focus to the file list fallback (T-0009, T-0010); the file trash path (`onMoveToTrash` in `DockspaceFilesPage.tsx`) has no dialog and no focus handling, so that code does not run.

## Acceptance criteria
1. After a successful Move to Trash on a file from its row menu (desktop menu button, right-click/ContextMenu/Shift+F10 menu, and the phone item menu), focus moves to a nearby row (the next row, or the previous one if it was the last) or, if the list is now empty, the file list fallback. It never lands on `body`.
2. The focus ring shows on `:focus-visible` after keyboard use, as in T-0010; no ring for mouse users.
3. If the trash request fails, the row stays and focus returns to that row (or its menu trigger), not `body`.
4. The status line confirmation from T-0011 ("File moved to trash." / "Failed to move file to trash.") and the existing dialog focus behavior do not change.
5. Web tests cover focus after a successful file trash (middle row, last row, only row) and after a failed one.

## Code review (round 1)
PR #29 at `0aff983` (4 files vs main). Ran the 9 new tests in the task worktree: all pass.

C1 (suggested weight: non-blocking). `apps/web/src/components/files/rowRemovalFocus.ts:62-73` together with `apps/web/src/styles/layout.css:741-745` and `:976-981`.
- What: the code moves focus to the next row after a mouse trash too, not only after keyboard use. Rows highlight on `.resource-list__item:focus-within`: a 1px inset accent box-shadow, an accent bottom border and a tinted background, and the row's actions trigger shows. Before this PR, a mouse user's focus fell to `body` after the trash, so no row was highlighted. Now, in Chrome and Firefox (where a click focuses the menu item), the row that moves up under the pointer gets that highlight.
- Why it matters: AC 2 says "no ring for mouse users". The `:focus-visible` rules (list outline, trigger) behave correctly. The row's `:focus-within` box-shadow looks like a ring, though, and stays until the user clicks somewhere else. The same thing already happens when a dialog opened with the mouse returns focus to its row (T-0009). This PR does not introduce the pattern, but it extends it to a path that had no highlight before.
- Fix (either one): (a) accept it as the existing row-focus look (the engineering notes already say "rows keep their existing focus highlight") and record that decision; or (b) limit the row highlight to keyboard focus, for example `.resource-list__item:has(:focus-visible)` in place of `:focus-within` for the box-shadow and border. That also changes the dialog-return case, so a tester should check it.

No other findings. Checked:
- Correctness. `useMoveToTrash` awaits the `files` invalidation and refetch before `mutateAsync` resolves, so the row is normally gone within the 10-frame retry. If it is still there after that, focus stays on the trigger, because focus is moved only when it is on `body`. Neighbours are taken from the row's own list (`[data-row-path]` in the `ul` with `data-dialog-focus-fallback`, which is always mounted, including the empty state), so a folder row can be a neighbour and pending rows are skipped. Two trashes running at once do not take focus from each other.
- Failure path: the row stays and focus returns to the trigger or the row; the T-0011 status messages are unchanged, in the same try/catch.
- Layout: the helper sits in `components/files` next to `useDialogDismiss.ts`. The only change to `useDialogDismiss.ts` is three new exports. Tests are in `src/tests`. No backend or data changes.
- Tests cover AC 5 (middle, last and only row, failure from the trigger and from the row menu), plus the row-opened menu, the phone layout, focus while the request runs and not taking focus back. The phone path is exercised through Shift+F10, which uses the same `data-return-focus="row"` path as press-and-hold. AC 2 (the `:focus-visible` ring) is CSS only and has no jsdom test, as in T-0010.
