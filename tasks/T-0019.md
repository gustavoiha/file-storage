# T-0019 Trash page restore errors name the item that failed
Issue: #42
Request: #5
Origin: T-0018
Status: review

## Goal
On the trash page, a failed restore shows one page-level message (`restoreErrorMessage` in `apps/web/src/pages/TrashPage.tsx`) that does not say which item failed, and starting any other restore clears it. When two trashed items share a path, or several restores run at once, the user cannot tell which item the message refers to, and a second restore can hide the first failure.

## Acceptance criteria
1. A restore error names the item it refers to, using the same description the row uses (path plus trashed date and time), e.g. "Could not restore /docs/report.txt (trashed <date, time>): <error>".
2. Starting a restore on a different row does not clear an earlier row's error. An error clears when the same row is retried, when that item leaves the trash, or when the user dismisses it.
3. If several restores fail, every failure stays visible (or is listed) until it is cleared as above.
4. Unit tests cover: an error naming the right copy when two trashed items share a path, and a second restore not clearing the first failure. Build, typecheck and tests pass.
5. The user sees a restore error without scrolling: in a trash list longer than the viewport, a failed restore on a row near the bottom shows its error next to that row, or scrolls the error into view. (Added from T-0018 test round 1, finding 1.)

## Code review (round 1)
PR #45 at de6c848. AC 1-5 are met in the code: errors are kept per row id with the copy's `deletedAt`, shown only while that same copy is in the trash, cleared on retry of that row or Dismiss, not by other rows, and each error scrolls itself into view. Tests cover AC 1-5, including two copies of one path, a second restore not clearing the first failure, and a re-trashed copy not inheriting an old error. AGENTS.md layout is unaffected (web only).

- **C1** (suggested: blocking) `apps/web/src/components/files/FileList.tsx`, `FlatRowError` (Dismiss button, ~line 172) and `onDismiss` wiring (~line 270). Pressing Dismiss removes the error together with the Dismiss button itself, and nothing moves focus, so a keyboard or screen-reader user who dismisses an error lands on `<body>`; the next Tab starts again from the top of the page, far from the row in a long trash list. This is the same class of focus loss T-0009 fixed for dialogs, on a control this PR adds. Fix: after dismissing, move focus to that row's Restore button (e.g. keep a ref to the row's action button in `FlatFileList`, or have `FlatRowError` take an `onDismissed` focus callback), and add a test that after clicking `Dismiss error for <row>` the focused element is `Restore <row>`.
