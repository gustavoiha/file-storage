# T-0031 Gallery: show loading status while a background refetch delays the next page
Issue: #69
Request: #65
Origin: T-0029
Status: done

## Goal
In the media gallery, automatic loading of the next page waits while any background refetch of the media query runs (window focus after `staleTime`, or an invalidation after an upload, trash or album change). A refetch re-requests every loaded page one after another, so with several pages loaded it can take a few seconds. During that wait the reserved footer (`role="status"`) in `apps/web/src/pages/dockspaceMedia/VirtualizedMediaGrid.tsx` is empty, because its text shows only for `isFetchingNextPage`, so a user who reaches the unloaded bottom gets no feedback until the next page arrives.

## Acceptance criteria
1. While a background refetch of the media query runs, there is a next page and no remembered next-page error, the footer's `role="status"` region shows "Loading more media..." (the footer space is already reserved, so tile layout does not change).
2. The text is cleared when nothing is loading, and is not shown while the next-page error with Try again is shown, nor in album views.
3. The held-refetch test in `DockspaceMediaPaging.test.tsx` expects the status text while the refetch runs and the next page request after it ends. Build, typecheck and tests pass.

## Test report (round 1)
PR #71 at `65ef9fd`, deployed to the dev site with `test-deploy.sh T-0031 web`. Headless Chromium (no WebKit), test user 1, the "T-0026 media" dockspace. For paging, the `/media` list responses were replaced in the browser with synthetic pages of 120 (600 items in total, 0.3 s per page, or 2-3 s while "slow" to hold a refetch). A background refetch was started the way React Query sees a return to the tab (`visibilitychange` hidden then visible, after the 10 s `staleTime`), and once by a real trash (two tiny PNGs were uploaded, then trashed through the gallery and purged from trash; the gallery and trash are empty again). Scripts: `$LOCAL/logs/T-0031/scripts/` (`refetch.mjs`, `blink.mjs`, `more.mjs`, `trash.mjs`, `upreal.mjs`, `regress.mjs`). Screenshots: `$LOCAL/logs/T-0031/`.

Passed:
- AC1, desktop 1440x900 and phone 390x844 (touch): with 2 pages loaded, a refetch started, then the user reached the end of the loaded media. "Loading more media..." showed in the `role="status"` footer within 400 ms, while only the refetch was in flight (no next-page request yet). It stayed through the end of the refetch and the next-page request (c240, sent about 5.9 s later, right after the refetch), with no blank between them: a MutationObserver recorded only "" -> "Loading more media..." (322 ms) -> "" (6047 ms). At most 1 request in flight. Footer height stayed 40 px, and the tile positions were identical before and during the refetch. Screenshots: `d-bottom-during-refetch.png`, `p-bottom-during-refetch.png`, `d-bottom-next-page.png`, `p-bottom-next-page.png`.
- AC2 / round-1 C1, at the top of the gallery: a refetch of 2 pages (about 6 s) recorded no status text at all, on desktop and phone (`d-top-during-refetch.png`, `p-top-during-refetch.png`). A real trash of a file from the top of a 2-page gallery (which invalidates the media query) also recorded no status text during its refetch.
- AC2: the text is cleared when nothing loads (empty after each refetch and next page). With the next-page error and Try again shown, a refetch kept the status empty next to the error (`d-error-during-refetch.png`); when the refetch succeeded, the error cleared and the normal next-page text showed for the next page. Album view: no footer and no status during a refetch (`d-album-during-refetch.png`). No next page (60 items): no footer during a refetch.
- Scrolling slowly through 5 pages: requests c120 to c480, one at a time; status only "" or "Loading more media..."; no footer at the end. The phone next-page status shows too (`p-next-page-status.png`).
- Accessibility: axe (wcag2a/aa, 21a/aa) found 0 violations on desktop with the refetch status showing and on phone with the next-page status showing. Tab reaches the first tile with focus-visible, Enter opens the preview and Escape closes it. The grid size toggles still work.
- Nearby pages: the dockspace tabs and a generic dockspace load. No console errors except the expected ones: a synthetic 500 in the error test, and 404s for preview requests on synthetic media ids.

Findings:
1. **Major (already on main, not changed by this PR): a file uploaded from the media gallery does not appear in the gallery until the page reloads or the user comes back to the tab.**
   - Steps: open a media dockspace, upload one image with the gallery's Upload button, and wait.
   - Expected: the new image appears in the gallery after the upload finishes.
   - Actual: the Uploads panel shows the upload as done, but the gallery stayed at the old tile count for 25 s and sent no `/media` request. The file showed only after a reload. `useUploadFile` in `apps/web/src/hooks/useFiles.ts` invalidates `files` and `media-duplicates`, but not `media`. The gallery uses that hook (`useDockspaceMediaController.ts`). So an upload does not start a gallery refetch, although the task goal lists one as a trigger.
   - Screenshot: `d-real-after-upload.png`. Script: `scripts/upreal.mjs`.
2. **Minor (already on main): the "Move to trash" dialog stays on "Moving..." until every loaded gallery page has been fetched again.**
   - Steps: load 3 pages of the gallery, select a tile, then choose Trash selected and Move to trash.
   - Expected: the dialog closes when the trash request succeeds.
   - Actual: `useTrashFilesBatch` awaits the invalidations in `onSuccess`, including the media refetch, which fetches every loaded page one after another. So the dialog shows "Moving..." for the whole refetch. With a held refetch (3 pages, 2.5 s each), it was still "Moving..." after 1.5 s. On a large library with slow pages, this is several seconds. A side effect: a trash at the end of the gallery runs its refetch behind the modal, so the new status text is not seen there.
   - Screenshot: `d-trash-bottom-during-refetch.png`. Script: `scripts/trash.mjs`.

Not covered: real WebKit/iOS Safari, and a real refetch after an upload (finding 1: there is none).
