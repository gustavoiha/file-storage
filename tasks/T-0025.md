# T-0025 Failed folder listing stays steady during uploads and folder creates
Issue: #56
Request: #31
Origin: T-0024
Status: testing

## Goal
On the dockspace files page, when the open folder's listing has failed (error with Try again shown, T-0024), an upload or folder create into that folder should not disturb the error state or lose the new item:
- The refetch that follows the upload or create (and any other background refetch not started from Try again) removes the error and Try again for a moment and re-adds it (screen readers may announce it again), and focus on Try again moves to the list. React Query clears `error` while a query with no data refetches, and `listingFailed` in `apps/web/src/pages/DockspaceFilesPage.tsx` only stays true during a Try again retry (`isRetryingListing`).
- A folder created into the failed folder stays "Creating..." until the listing loads, and an uploaded file disappears from the list once its upload finishes, because pending rows are cleared against a fetched listing that is missing. Pre-existing on main.

## Acceptance criteria
1. While the open folder's listing is unknown and its last request failed, any background refetch (after an upload, a folder create, discovery) keeps the error with Try again mounted, does not re-insert the alert, and leaves focus on Try again if it was there. Same on desktop and phone.
2. A folder created into a failed folder no longer stays "Creating..." indefinitely, and a file uploaded into it does not silently disappear: either the item stays visible as created/uploaded until the listing loads, or the page tells the user the item was saved and the listing will show it after Try again.
3. Try again, the empty state for a truly empty folder, and the T-0024 behaviour (no empty state while the listing failed) are unchanged.
4. Unit tests cover the background refetch keeping the alert and focus, and the create/upload into a failed folder. Build, typecheck and tests pass.

## Code review (round 1)
Reviewed PR #59 at 8fa0900. The background-refetch fix (AC1) is sound: `lastListingFailure` keeps the alert and Try again mounted through any refetch, only Try again marks the button busy, and the tests (desktop, phone, MutationObserver mid-refetch, create case, background load) cover it. Two findings on the saved-item records (AC2):

- **C1 (suggested: blocking)** `apps/web/src/pages/DockspaceFilesPage.tsx` ~lines 437-446 (drop effect) with ~lines 1635-1641 (`pendingFolderPathsInList`). The drop effect removes every record that `childEntryInFolder(currentFolder.fullPath, item)` matches, i.e. every record *under* the open folder at any depth, not only the records made for that folder. Scenario: `/A`'s listing fails, the user creates `Receipts` in `/A` (record `/A/Receipts`, "Creating..." row hidden, status line shown), then goes up to `/` (root listing loaded): `childEntryInFolder('/', '/A/Receipts')` matches, so the record is dropped although `/A` never loaded. Back in `/A` (listing still failing), `savedUnlistedItems` is empty, `pendingFolderPathsInList` returns `addFolderDialog.pendingFolderPaths` unfiltered, and `useAddFolderDialog` never cleared `/A/Receipts` (it clears only against a fetched listing that contains it): the row is back to "Creating..." indefinitely and the "was created" line is gone. That is the AC2 bug again after a single up-and-back navigation; the same applies to an upload record (the line disappears). Why it matters: AC2 says the created folder must no longer stay "Creating..." indefinitely. Fix: store the open folder's path in each record when it is made (`folderPath` from `listingStateRef`), drop a record only when the open folder is exactly that folder and its listing is loaded, and build the message and the `pendingFolderPathsInList` filter from records whose `folderPath` equals the open folder. Add a test: create into failed `/A`-like folder, open the root (loaded), reopen the folder (still failing), expect no "Creating..." and the line still shown.
- **C2 (suggested: non-blocking)** `apps/web/src/pages/DockspaceFilesPage.tsx` ~lines 428-436 (`recordSavedIfUnlisted`) with `childEntryInFolder`. The record is checked against the folder open when the save *finishes*, not the folder the item went into, and any descendant is accepted. Scenario: the user starts an upload in a loaded folder `/B`, opens the root before it finishes, and the root's listing has failed: `/B/file.txt` is recorded and the root shows `"B" was uploaded. It will show here after Try again.`, although `B` already existed and nothing new was uploaded into the root. Same for a create submitted in one folder that finishes after navigating to a failing ancestor. Why it matters: the status line (a live region) announces something false. Fix: record only when the item's target folder (the folder open when the create/upload started: the dialog's `currentFolderPath`, or the item's parent for a single file) equals the open folder, keeping the top-folder mapping only for a folder upload started in that folder. Can share the `folderPath` field from C1.

## Review decisions (round 1)

False status text introduced by this PR, and the fix shares C1's `folderPath` field, so it goes in the same change.
