# T-0018 Trash page handles two trashed items with the same path separately
Issue: #39
Request: #5
Origin: T-0013
Status: engineering

## Goal
On the trash page, the same file path can be in the trash more than once (a file trashed, re-created, trashed again). The page tracks the pending purge and restore by path (`pendingSecondaryActionPath`, `purgeFilePath` and `pendingRestorePath` in `apps/web/src/pages/TrashPage.tsx`), and the purge and restore API calls take only the path. While testing T-0013, purging one copy set both rows to "Purging..." and once left the Purge dialog open until a reload. Make each trashed item act on its own.

## Acceptance criteria
1. With two trashed items that share a path, starting Purge now or Restore on one row shows the pending label only on that row.
2. Purge now and Restore act on the item the user picked, and the result is defined and tested in the backend (which copy is purged or restored, what happens to the other one); no request silently acts on both or on the wrong one.
3. After a successful purge, the dialog closes and the trash list shows the remaining copy; after a failure, the dialog shows the error and can be closed.
4. Rows with the same path have distinct React keys and accessible names that tell them apart (e.g. the trashed date).
5. Unit tests cover the duplicate-path case in the trash page and in the backend purge/restore handlers. Build, typecheck and tests pass.
