# T-0024 Failed folder listing shows the error without the empty state
Issue: #52
Request: #31
Origin: T-0015
Status: done

## Goal
On the dockspace files page, opening a folder whose listing request fails shows the "Request failed" alert together with the empty state ("This folder is empty" / "Upload your first files"). The folder is not known to be empty, so the empty state and its upload call to action are wrong there. Today the file list gets the empty state whenever the listing is not loading (`emptyState={filesQuery.isLoading ? ... : emptyDockspaceState}` in `apps/web/src/pages/DockspaceFilesPage.tsx`), also after an error.

## Acceptance criteria
1. When the current folder's listing request fails, the page shows only the error (with a way to try again), not "This folder is empty" or "Upload your first files". Same on desktop and phone.
2. A folder that loads with no items still shows the empty state as today.
3. After a successful retry, the folder shows its contents, or the empty state if it really is empty.
4. The error is announced (`role="alert"`) and the retry control is keyboard reachable; focus does not fall to `body` when the retry starts or ends.
5. Unit tests cover the failed listing (no empty state), the truly empty folder and the retry. Build, typecheck and tests pass.

## Notes

The fix follows the folder info Try again pattern (same button stays mounted, `aria-disabled`/`aria-busy` while busy, retry tracked by folder id because React Query clears `error` while a query with no data refetches, focus moved to the list's `data-dialog-focus-fallback` only when it fell to `<body>` and only for the same folder). - **C1 (non-blocking)** `apps/web/src/pages/DockspaceFilesPage.tsx` lines 1612-1616 (`filesErrorAlert`) and 1672 (`emptyState`), with `FileList.tsx` line 1155/1210. When the open folder's listing failed and the folder then has a pending entry (the user creates a folder or starts an upload into it from the toolbar, which stays available), `FileList`'s `hasEntries` is true so the `emptyState` slot (now the only place the error lives) is not rendered, and `filesErrorAlert` is suppressed because `hasListing` is false. The error and Try again disappear while the pending row is shown; before this PR the alert stayed above the list. It comes back only if the refetch after the mutation also fails. Also, if Try again had focus when the pending row appeared (e.g. a drop upload), it unmounts without the focus restore, since `listingFailed` did not change. Fix: render the error alert (with Try again) above the list when `listingFailed && hasEntries`-equivalent, e.g. make `filesErrorAlert` show `listingErrorState` when `listingFailed` and the folder has pending entries, or simpler, always render the failed-listing alert above the list and pass a neutral empty slot (no empty state, no "Loading...") when `listingFailed`. Add a test: failed listing, start a pending folder create, the alert is still shown.

## Review decisions (round 1)
Judged PR #55 at d9e1d85.
- **C1 - critical.** Confirmed: `FileList` counts pending folders/uploads in `hasEntries`, so the empty slot that now holds the failed-listing alert is not rendered, and `filesErrorAlert` needs `hasListing`; with a failed listing plus a pending create/upload, the error and Try again vanish (on main the alert stayed above the list), and a focused Try again unmounts to `<body>` with no restore. That brings back a case main handled and breaks the engineering-lessons focus rule ("ask what happens to focus when the condition flips"). Fix: while `listingFailed`, keep the alert with Try again mounted when the folder has pending entries (e.g. render it above the list and pass a neutral empty slot), and test failed listing + pending folder create keeps the alert, plus focus on Try again survives a pending row appearing.
