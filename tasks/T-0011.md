# T-0011 Status line confirms Move to Trash and drops stale messages
Issue: #26
Request: #5
Status: filtering
Origin: T-0010

## Goal
The status line above the file list (`role="status"`, fed by `moveFilesSummary` in `DockspaceFilesPage.tsx`) is not cleared or updated when a folder is moved to the trash (`onTrashFolderSubmit`) or a file is moved to the trash (`onMoveToTrash`). After a move, then Move to Trash, it keeps showing the old "Folder moved from ... to ..." message, and nothing confirms the trash. Sighted users see a stale message, and screen reader users hear no confirmation.

## Acceptance criteria
1. After a folder is moved to the trash (confirmation dialog), the status line shows a short confirmation such as "Folder moved to trash." and no earlier message remains.
2. Moving a file to the trash from the row menu also clears any stale status message (and shows a matching confirmation if that fits the design).
3. If the trash request fails, the status line does not claim success; the dialog error behaves as today.
4. The confirmation is announced through the existing `role="status"` region; focus behavior from T-0009 and T-0010 does not change.
5. Web tests cover the status after a successful folder trash, after a failed one, and that a previous move message is replaced.

## Code review (round 1)
PR #27. Diff matches the criteria: both trash paths clear the old message when they start, set "Folder moved to trash." / "File moved to trash." on success, a failed folder trash leaves no status text and keeps the dialog error, and a failed file trash shows "Failed to move file to trash." (the promise is now awaited, so there is no unhandled rejection). The T-0009/T-0010 focus code is untouched. The 5 page tests cover success, failure and replacing a previous move message for both paths. No AGENTS.md, data or engineering-lessons concerns (web only, no backend change).

- **C1** (non-blocking) `apps/web/src/components/files/FileList.tsx:926-930` together with `apps/web/src/pages/DockspaceFilesPage.tsx:612` and `:857`. The `role="status"` paragraph is mounted only while `statusMessage` is non-empty. This PR now sets the message to `null` before each trash request and sets the confirmation afterwards, so the region is always removed and then added back with its text already inside. Many screen reader and browser pairs (VoiceOver with Safari in particular) do not announce a live region that is added to the page with its content, only changes to a region that already exists. So criterion 4 (the confirmation is announced) may hold in jsdom but not for real screen reader users. The move confirmations already use the same mount-with-text pattern (`openMoveFolderDialog` clears too), so this is mostly pre-existing, but this task exists for the announcement. Fix: always render the `role="status"` element in the sticky area (empty when there is no message, visually collapsed with CSS) and change only its text. Tests can then assert that the same status element goes from empty to "Folder moved to trash.".
- **C2** (non-blocking) `apps/web/src/pages/DockspaceFilesPage.tsx:611-620`. The file trash handler has no guard against results arriving out of order. If a file trash is still pending while the user moves a folder (or starts a second trash), whichever request finishes last wins, so a late "File moved to trash." can replace a newer "Folder moved from ..." message, or a failure message can show after a later success. This is a rare edge case and the text stays true for the action it names. Optional fix: keep a request counter in a ref and set the summary only if the request is still the latest one.
