# T-0019 Trash page restore errors name the item that failed
Issue: #42
Request: #5
Origin: T-0018
Status: deploying

## Goal
On the trash page, a failed restore shows one page-level message (`restoreErrorMessage` in `apps/web/src/pages/TrashPage.tsx`) that does not say which item failed, and starting any other restore clears it. When two trashed items share a path, or several restores run at once, the user cannot tell which item the message refers to, and a second restore can hide the first failure.

## Acceptance criteria
1. A restore error names the item it refers to, using the same description the row uses (path plus trashed date and time), e.g. "Could not restore /docs/report.txt (trashed <date, time>): <error>".
2. Starting a restore on a different row does not clear an earlier row's error. An error clears when the same row is retried, when that item leaves the trash, or when the user dismisses it.
3. If several restores fail, every failure stays visible (or is listed) until it is cleared as above.
4. Unit tests cover: an error naming the right copy when two trashed items share a path, and a second restore not clearing the first failure. Build, typecheck and tests pass.
5. The user sees a restore error without scrolling: in a trash list longer than the viewport, a failed restore on a row near the bottom shows its error next to that row, or scrolls the error into view. (Added from T-0018 test round 1, finding 1.)

Pressing Dismiss removes the error together with the Dismiss button itself, and nothing moves focus, so a keyboard or screen-reader user who dismisses an error lands on `<body>`; the next Tab starts again from the top of the page, far from the row in a long trash list. Findings:
1. **nit** - When two restores fail close together, a later error can push an earlier one partly below the viewport. Steps: in a long trash list, start Restore on the second-to-last and then the last row so that both fail and the last row's failure is shown first. Expected: both errors fully in view, or the last-shown error stays in view. Actual: the last row's error had scrolled itself into view, then the error above it appeared and pushed it down: it measured top 877 / bottom 915 in a 900 px viewport, so about 15 px was cut off (step C in `results-run.json`). It is still next to its row, so AC 5 holds. Screenshot: none at that moment (`d1440-2-three-errors.png` was taken after scrolling).
2. **minor (not caused by this PR)** - After a successful Restore, or a Purge confirmed in its dialog, the row leaves the list and keyboard focus falls to `<body>`. The next Tab starts again from the top of a long trash list. Steps: focus or click `Restore` on a trashed file whose restore succeeds, then check `document.activeElement`. Expected: focus moves to a nearby row (next row's Restore, or the list) as T-0012 did for Move to Trash in the file list. Actual: `BODY` (step E in `results-run.json`, `afterPurge` in `results-phone.json`). This happened the same way before PR #45 (T-0018 behavior), so it may need its own task. Screenshot: `p390-3-after-purge.png`.
- Test harness note (not an app issue): in the first run a Playwright route race let one intended-to-fail restore of `t19-b.txt` go through, so it was really restored. I trashed it again and re-ran with a fixed script.
