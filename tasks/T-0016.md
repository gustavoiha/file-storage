# T-0016 Keep folder file counts current after moving files
Issue: #36
Request: #31
Origin: T-0014
Status: review

## Goal
On the files page, a folder row's "N files" count goes stale after files are moved into or out of that folder:
it keeps the old number until the page is reloaded. In `apps/web/src/pages/DockspaceFilesPage.tsx`,
`discoverFolderChildren` runs once per folder node (skips nodes whose `childFolderNodeIds` and `directFileCount`
are set), and `onMoveFilesSubmit` does not update or invalidate the affected nodes, so `folderFileCounts` keeps
the old value. Keep the counts current.

## Acceptance criteria
1. After moving one or more files into a subfolder of the current folder (selection mode, Move dialog), that
   subfolder's row shows the new file count (e.g. "0 files" becomes "1 file") without a page reload.
2. After moving files out of a folder whose count is shown (e.g. into a sibling or the parent), the source
   folder's count (row and sidebar tree) is updated too, also when only some of the files moved.
3. Counts shown in the sidebar folder tree stay consistent with the folder rows after a move.
4. No extra full re-discovery of the whole tree: refresh only the folders affected by the move (or adjust their
   counts locally from the move response).
5. Unit tests cover the count update after a successful and a partly failed move. Build, typecheck and tests pass.

## Code review (round 1)
PR #37 (commit 274b043). Checked: `applyFileMovesToDiscoveredFolders` against the backend `moveFiles` response (`from` and `to` are normalized full paths, so `parentFolderPathFromPath` matches the discovered `fullPath` keys, root included); same-folder entries (backend reports them as `moved`) are skipped; undiscovered folders stay `null` and get fresh data on discovery; all shown counts (rows in every column) read the one `folderFileCounts` map, so AC3 holds. The current folder is both adjusted by the delta and re-merged from its refetched listing: `useMoveFiles` awaits `invalidateQueries`, but TanStack Query notifies observers on a `setTimeout(0)`, so the delta update is queued before the render with the new listing and the absolute recount from `mergeDiscoveredFolderItems` lands last. Correct as written. Branch is mergeable on current main (T-0014's #35 merged, it touched other files), so no rebase conflict.

- **C1** (non-blocking) `apps/web/src/tests/pages/DockspaceFilesPage.test.tsx:422` and `:451`: the tests do not cover the source folder when it is the open folder and its listing refetches after the move. `useFiles` is mocked with a fixed, cached result, so the listing never changes and the re-merge effect (`DockspaceFilesPage.tsx:327`) never runs after the move. In real use the source is usually the open folder, and its count is set twice: once by the delta (`:759`) and once by the recount from the refetched listing. This is correct only because the delta runs first. If that order flips (for example a future `useMoveFiles` that updates the cache with `setQueryData`, or a scheduler change), the source folder loses the moved files twice. The first test cannot catch this because 1 - 2 is clamped to 0 by `Math.max`. Fix: add a test where the open source folder has 3 files, the mocked listing for that folder changes to 2 files when the move resolves, and the source row (in the parent column) shows "2 files", not "1 file".
