# T-0020 Confirmation dialogs take focus when they open
Issue: #43
Request: #5
Origin: T-0018
Status: deploying

## Goal
The confirmation dialogs "Purge file now" (`apps/web/src/components/files/ConfirmPurgeFileDialog.tsx`, trash page) and folder Move to Trash (`apps/web/src/components/files/ConfirmFolderTrashDialog.tsx`) do not move focus into the dialog when they open. After Enter on "Purge now", keyboard focus stays on the row button behind the `aria-modal` dialog, so Tab and screen readers start outside the dialog. The Rename, Move and New folder dialogs already set initial focus with `autoFocus`.

## Acceptance criteria
1. When the Purge dialog or the folder Move to Trash dialog opens, focus moves into it. For these destructive confirmations the initial focus is the Cancel button, so pressing Enter right away does not delete anything.
2. Tab and Shift+Tab stay inside the open dialog (or, at minimum, the first Tab after opening lands on a dialog control, not on the page behind it).
3. Escape, Cancel and backdrop still close the dialog and return focus to the opener (no regression of T-0009 / T-0018 behavior); after a successful purge or folder trash, focus handling stays as it is today.
4. Unit tests cover initial focus for both dialogs. Build, typecheck and tests pass.

## Code review (round 1)
PR #44 at 389e653. 1 finding (non-blocking). Criteria 1, 3 and 4 are met: Cancel takes focus on open in both dialogs, Enter right after opening closes without submitting, the opener is still read in the opening render (before `autoFocus` runs), and FileList's menu-close `setTimeout` does not steal focus from Cancel because it only acts when focus is on body. The new test file passes locally (14 tests).

- **C1 (non-blocking)** `apps/web/src/components/files/useDialogDismiss.ts:81-106` (`trapDialogTabKey`, attached as the dialog's `onKeyDown` in both dialogs). The trap only runs while focus is already inside the dialog. While a purge or folder trash is submitting, both buttons are disabled, and the browser moves focus from the pressed button to `body`. Tab keydown then targets `body`, the dialog handler never runs, and Tab moves to the page behind. Checked in headless Chromium with the same handler and DOM shape: focus Purge, disable both buttons, press Tab → focus lands on a row button outside the dialog, and the handler is called 0 times. After a failed submit (error shown, buttons re-enabled), focus stays on `body` and Shift+Tab also leaves the dialog for the page behind. So the PR's claim "Tab is swallowed when no control is tabbable" does not hold in a real browser. The test `keeps focus from leaving on Tab while both buttons are disabled` (`ConfirmDialogsFocus.test.tsx:117-129`) dispatches keydown from the disabled Cancel button, which a browser would not do because a disabled button cannot keep focus, so it passes in jsdom only. Why it matters: criterion 2 asks for Tab and Shift+Tab to stay inside the open dialog. The minimum fallback (first Tab after opening lands on a dialog control) is met, which is why this is non-blocking. Fix: register the Tab handling as a `document` keydown listener while the dialog is open (`useDialogDismiss` already registers one for Escape), using a dialog ref. Keep the current wrap logic: `activeIndex === -1` already covers focus on `body`. Then rewrite the disabled-state test to dispatch Tab from `document.body`, and add a test for Shift+Tab after a failed submit.
