# T-0023 Trash page keeps focus on the row after a failed restore
Issue: #50
Request: #5
Origin: T-0021
Status: review

## Goal
On the trash page (`apps/web/src/pages/TrashPage.tsx`, flat `FileList`), after a failed Restore, keyboard focus is on `body`: while the request runs the row's Restore button is disabled ("Restoring..."), the browser blurs it, and nothing puts focus back when the per-row error appears. The next Tab starts from the top of the page. Focus should stay with the row that failed.

## Acceptance criteria
1. After a failed Restore, if focus fell to `body` during the request, it moves to that row's Restore button (or the row's error Dismiss button), with a visible focus ring for keyboard users. Never `body`.
2. If the user moved focus elsewhere during the request, it is left where it is.
3. The per-row restore error (T-0019) is still announced, and Dismiss still returns focus to the row's Restore button. Successful restores keep T-0021's focus handling.
4. A unit test covers focus after a failed restore in a way that reproduces the blur of the disabled button (jsdom does not blur disabled elements, so the test must simulate it). Build, typecheck and tests pass.

## Notes
- Pre-existing on main (`disabled={isActionPending}` on the Restore button in `FileList.tsx`); not caused by T-0021 (PR #49). Builds on T-0021's focus-after-removal code in the flat `FileList`, so start after PR #49 is merged.
- The same symptom inside the Purge dialog after a failed purge is already covered by T-0022 (#48); keep this task to the inline Restore.

## Code review (round 1)
PR #53 (commit 112c7d7). No findings.
- Checked: `FlatFileList`'s new failure-focus `useLayoutEffect` (`apps/web/src/components/files/FileList.tsx`) waits while the row's Restore button is still disabled and re-runs on `pendingActionFileIds`, so it works whether or not the `catch` and `finally` updates in `TrashPage.onRestore` are batched (React 18 batches them; the wait is a safe fallback). It moves focus only when `focusIsLost()`, and only to the failed row's own button, so another row's still-running restore and focus the user moved elsewhere are left alone (criteria 1, 2).
- Restore button is disabled only by `isActionPending`, so the request cannot stay waiting after the restore settles. A row that is gone when the failure arrives is marked handled without moving focus; `useRestoreFile` only invalidates the trash on success, so the row stays after a failure.
- T-0019 alert and Dismiss, T-0021's `focusAfterRemoval` path and the Purge dialog (T-0022) are untouched; separate handled-request refs, so the two requests do not interfere (criterion 3).
- Tests (`apps/web/src/tests/pages/TrashPage.test.tsx`): the `MutationObserver` blur simulation follows the engineering lesson, asserts focus is on body mid-request, and covers failure, focus moved elsewhere, concurrent restores, success and Dismiss (criterion 4). I did not run them (not in my permissions); engineering reports typecheck, tests and build pass, and the PR has no CI checks.
- Not verifiable in code: the focus ring after the programmatic move. The Restore `Button` uses the default `:focus-visible` outline; testing should Tab-check it on dev after a keyboard-activated failed restore.
