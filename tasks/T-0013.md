# T-0013 Show the row focus highlight only after keyboard use
Issue: #30
Request: #5
Status: filtering
Origin: T-0012

## Goal
File list rows show a focus highlight on `.resource-list__item:focus-within` (inset 1px accent box-shadow, accent bottom border, tinted background; the actions trigger appears). Focus is moved to a row after mouse actions too: when a dialog closes (T-0009) and, with T-0012, after Move to Trash on a file. In browsers where a click focuses the menu item, mouse users then see a ring-like highlight on a row they did not pick, until they click elsewhere. Keep the highlight for keyboard users; drop it for mouse users.

## Acceptance criteria
1. The row focus highlight (box-shadow and accent bottom border) shows only when focus in the row came from the keyboard (e.g. `.resource-list__item:has(:focus-visible)` or the row matching `:focus-visible`), in the current and ancestor columns and on phone rows.
2. After a mouse action that moves focus to a row (dialog close from T-0009, Move to Trash from T-0012), that row shows no focus highlight. The hover style is unchanged.
3. After keyboard use (Tab, arrow keys, Escape or a dialog closed with the keyboard, Move to Trash from the keyboard), the focused row still shows the highlight, and the actions trigger is still visible and reachable when focus is inside the row.
4. The empty-state row, the T-0010 list fallback ring and the T-0006 card rings do not change.
5. Checked in Chrome, Firefox and Safari; browsers without `:has()` support keep a visible keyboard focus indicator.

Findings:
1. minor (verification gap, not a defect) — AC 5 not checked in Firefox and Safari. Only Chromium is installed in `$LOCAL/tools` (no Playwright Firefox or WebKit), and I did not download browsers without approval. Steps: open a file folder in Firefox and in Safari (desktop and iOS), Tab into a row (ring expected), then Move to Trash with the mouse or a long press (no ring expected on the next row). Expected: same as Chromium. Actual: not run. The CSS uses standard `:has()`/`:focus-visible` and a `@supports not selector(:has(*))` fallback, so the risk is low, but each browser's focus-visible heuristic after a script `.focus()` differs (code review note).
2. minor (pre-existing, not from this PR) — keyboard focus on the current (`aria-current`) row in an ancestor column is not visible. Steps: desktop, open a folder, focus the highlighted folder row in the left column and press ArrowDown then ArrowUp. Expected: a focus indicator on the focused row. Actual: it looks the same as when not focused, because `.dockspace-column__row[aria-current]` comes after `.dockspace-column__row:focus-visible` with the same specificity and replaces its box-shadow and background, and the outline is off. Screenshot `$LOCAL/logs/T-0013/d1440-8-ancestor-kbd.png`. Same CSS on main.
3. nit — phone, mixed input: after keyboard use (a row has the ring), a long press on another row opens its menu with the ring on that row and an outline on the first menu item, because the long press does not move focus and Chromium keeps script focus `:focus-visible` after keyboard focus.
