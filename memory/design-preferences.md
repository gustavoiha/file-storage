# Human design preferences (owned by Design agent)
Each entry: preference, evidence (issue/comment link), date.

## Navigation and layout
- Prefers a Finder-style column view (Miller columns) for browsing folder hierarchies: every ancestor level is a visible column, the open folder is highlighted in its parent column, and the file preview is the last column on the right. Reason given: "all the information the user needs in a single place, neatly organised in a predictable manner". (T-0001, https://github.com/gustavoiha/file-storage/issues/5#issuecomment-7021776277, 2026-11-19)
- Values predictability and having everything in one place: favor layouts where position on screen tells the user where they are (path left to right, detail on the right) over layouts that change shape as you expand things. (T-0001, 2026-11-19)
- (inferred) Does not want the folder hierarchy to live only in a separate sidebar tree with a files-only main panel: a tree split from the listing reads as two places. (T-0001, rejected Option 2, 2026-11-19)
- (inferred) Prefers fixed, predictable structure over expand-in-place outlines whose indentation and pinned ancestors shift while scrolling. (T-0001, rejected Option 3, 2026-11-19)
- Detail views for a single item go in the right-hand detail slot of the column view, the same 420px panel as the file preview: folder info (T-0015) reuses the preview frame (header with icon, name, primary action, Close X; label; metadata list; Esc hint) and only one detail panel shows at a time. On phone the same detail opens as a full page with a back button, like the phone file preview. (T-0015, https://github.com/gustavoiha/file-storage/issues/33#issuecomment-7067560467, 2026-11-21)
- (inferred) For looking at information (not editing), prefers a non-modal panel beside the list over a modal dialog that blocks the page. (T-0015, rejected Option 1, 2026-11-21)
- (inferred) Comfortable with a richer info view (count tiles, size, created/modified, location, an Open action) rather than a minimal one-line glance card. (T-0015, chose Option 2 over Options 1 and 3, 2026-11-21)
- To switch between top-level containers (dockspaces), prefers browser-style tabs in the top nav (type icon + full name, as many as fit, then a "More (n) ▾" popover with a filter, + to create) over a Slack-style icon rail or a labelled sidebar. Reason given: "It feels more comfortable to use." (T-0026, https://github.com/gustavoiha/file-storage/issues/58#issuecomment-7077571334, 2026-11-22)
- (inferred) Global navigation chrome should not take width from the column view: put switchers in the existing top nav rather than in a persistent left rail or sidebar that narrows the Miller columns. (T-0026, rejected Options 1 and 2, 2026-11-22)
- (inferred) Items should be recognisable by their full readable names; initials-only tiles that need a tooltip to identify are less comfortable. (T-0026, rejected Option 1, 2026-11-22)
- Page-level actions such as New folder and Upload belong in a top bar (next to the breadcrumb, or the album button in the gallery) rather than in a side panel; background status (uploads) floats as the small UploadsCard (bottom right, collapsing to a progress pill; on phone bottom left beside the Upload pill) instead of a sidebar section or a toolbar badge. (T-0001 inferred, 2026-11-19; confirmed T-0030 choosing Option 1, https://github.com/gustavoiha/file-storage/issues/67#issuecomment-7080011483, 2026-11-22)
- Keep the screen uncluttered: do not keep secondary information (album lists, upload lists, action lists) always visible; put it behind a menu or a compact control and show only the current state (e.g. the current album name). Reason given: the other options "have way too much information in the screen". (T-0030, https://github.com/gustavoiha/file-storage/issues/67#issuecomment-7080011483, 2026-11-22)
- Keep different intents in separate menus: navigation (switching between albums, showing the current one) gets its own menu button; actions (Find duplicates, Trash, Detailed usage) go in the page's ⋯ options menu. Never mix navigation and actions in one dropdown or panel. (T-0030, same comment, 2026-11-22)
- In the media gallery, albums are switched from a single album menu button on the left of the toolbar (current album name + count + ▾, menu of All media and every album with the current one checked); on phone that button fills the toolbar and opens a full-screen album list with a back arrow. (T-0030, chose Option 1, same comment, 2026-11-22)
- (inferred) For a switcher inside a page (albums), prefers one menu button over a row of tabs or scrolling chips, even though top-level dockspaces use tabs: the in-page row was "too much information". (T-0030, rejected Option 3, 2026-11-22)
- (inferred) Does not want one catch-all menu/panel that folds a whole sidebar (albums, actions, uploads) together behind a single button with badges. (T-0030, rejected Option 2, 2026-11-22)
- Content areas should not be framed: no card (border, radius, padding, own background) around a main listing such as the gallery; the content runs to the edges. Media tiles are square, with no gap, no rounded corners and no border; hover, focus and selection are drawn inside the tile (tint, inset ring, check) and nothing lifts or moves. (T-0030, request https://github.com/gustavoiha/file-storage/issues/65, 2026-11-22)

## Touch / phone interaction
- On phone screens, enters multi-select from an explicit "Select items" entry in the folder's options (⋯) menu, which turns on a selection mode; not from a per-row "Select" action, not from a header button, and not from press-and-hold. (T-0005, https://github.com/gustavoiha/file-storage/issues/15#issuecomment-7039970641, 2026-11-20)
- On phone screens, wants no per-item ⋯ menu button on rows (files and folders): press-and-hold on the item opens that item's menu instead, and a normal tap keeps its primary action (preview/open). Keeps phone rows clean and gives each row one obvious tap target. (T-0005, same comment, 2026-11-20)
- (inferred) Press-and-hold on touch is for an item's menu (like a right-click), not for selecting; selection stays an explicit mode. (T-0005, rejected Option 3 long-press-to-select, 2026-11-20)
- On phone, a top-nav switcher collapses into a full-width "current item" bar under the top nav (icon, current name, count, ▾) that opens a full-screen list with a back arrow, like the phone file preview and folder info full page; not a left drawer and not a bottom sheet. (T-0026, chosen Option 3 over Options 1 and 2, 2026-11-22)
- Prefers reusing existing surfaces (the folder ⋯ menu, the desktop selection bar, the row action menu) over adding new chrome such as a header Select button, a full-width bottom action bar, a floating dock or a header (i) info button. Actions about the current folder go in its existing options menu: "Folder info" first in Dockspace options ⋯ (desktop) and Folder options ⋯ (phone); actions about a child folder go first in its row menu. (T-0005 rejected Options 1 and 3, 2026-11-20; confirmed T-0015 choosing Option 2 over the (i) button of Option 3, https://github.com/gustavoiha/file-storage/issues/33#issuecomment-7067560467, 2026-11-21; applied T-0030: Find duplicates, Trash and Detailed usage go in the gallery's ⋯ Gallery options, and on phone "Select items" is first in that menu, 2026-11-22)
