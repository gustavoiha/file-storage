# T-0021 Keep focus in the trash list after a restore or purge
Issue: #46
Request: #5
Origin: T-0019
Status: done

## Goal
On the trash page (`apps/web/src/pages/TrashPage.tsx`, flat `FileList`), a successful Restore, or a Purge confirmed in its dialog, removes the row, and keyboard focus falls to `<body>`. The next Tab starts again from the top of the page, far from where the user was in a long trash list. T-0012 fixed the same problem for Move to Trash in the file list; the trash page should behave the same way.

## Acceptance criteria
1. After a successful Restore of a trashed item, focus moves to the next row's Restore button, else the previous row's Restore button, else a fallback in the trash card (e.g. the list or the empty-trash message, focusable with `tabIndex={-1}`). Never `body`.
2. After a successful Purge confirmed in the Purge dialog, focus follows the same rule as criterion 1 once the dialog closes.
3. A failed Restore or Purge keeps today's behavior (focus stays on the row's control, or returns to the opener when the dialog is cancelled or closed); the per-row restore errors and Dismiss focus from T-0019 still work.
4. The focused fallback shows a visible focus ring for keyboard users (`:focus-visible`), as T-0010 does for the file list.
5. Unit tests cover: focus after a successful restore of a middle row, of the last row, and of the only row; focus after a successful purge. Build, typecheck and tests pass.

Findings:
1. **minor (pre-existing, not a regression)** — after a failed Restore, focus is on `<body>`, not on the row's Restore button. Steps: 1440x900, trash page, Tab to a row's Restore, press Enter, make the request fail (I rewrote the request's file node id so the API returns 404). Expected (criterion 3): focus stays on the row's Restore. Actual: when the request starts, the button becomes disabled with label "Restoring...", Chromium blurs it (focusout, no related target) and focus falls to `<body>`; when the error shows, the button is enabled again but focus stays on `<body>`, so the next Tab starts from the top of the page. The same happens inside the Purge dialog: after a failed Purge now, focus is on `<body>` while the dialog stays open (its buttons are disabled while it submits); Escape still returns focus to the row's Purge now. main has the same `disabled={isActionPending}`, so this is not caused by PR #49. The unit test "keeps focus on the row's Restore button after a failed restore" passes only because jsdom does not blur disabled elements. Suggested follow-up: after a failed restore, if focus fell to `<body>`, put it on that row's Restore button (or its Dismiss); in the dialog, put it back on Purge now or the error. Screenshots: `d1440-D-failed-restore.png`, `d1440-E-failed-purge.png`, `p390-P3-failed-restore.png`.
