# T-0005 Make multi-select reachable on touch phones
Issue: #15
Request: #5
Status: testing
Origin: T-0003

## Goal
On a touch phone, the "Select {name}" checkbox shows only on hover/focus, so there is no visible way to start multi-select (and then Move several files) by touch. Give touch users a clear way in.

## Acceptance criteria
1. At 390x844 with touch, a user can start selection mode on the files page without a keyboard or hover, using a visible control (e.g. a "Select" item in the folder options menu or the row `⋯` menu, or a long-press with a visible hint). The chosen pattern is described in the PR.
2. Once in selection mode on a phone, tapping rows toggles them, the checkboxes are visible, and the selection bar (Move, clear) works as on desktop. Leaving selection mode returns to normal tap-to-preview.
3. (Human decision 2026-11-20) On phone/touch screens: the Folder options menu has a "Select items" entry that turns on selection mode; the per-row `⋯` menu button is removed from every item (files and folders); pressing and holding an item opens that item's menu (same actions as the old `⋯` menu). A normal tap still previews/opens. Long-press must not also trigger the browser's native context menu or text selection.
4. Desktop behavior is unchanged (hover/focus reveal, click on the checkbox, keyboard). No new serious or critical axe violations. Web tests are updated and pass.

### Scope
- "Phone" means the existing phone layout: `isPhone = useMediaQuery(PHONE_LAYOUT_QUERY)` (`(max-width: 900px)`) in DockspaceFilesPage. Everything below applies only there. Desktop (>900 px) is unchanged: hover/focus checkbox, row `⋯` menu, right-click menu, keyboard, and today's "selection mode = at least one file selected" rule.

### 1. Enter selection mode: Folder options -> "Select items"
- `DockspaceOptionsMenu` variant `phone` (label "Folder options") gets a new first item **"Select items"**, followed by a separator, then the existing New folder / Upload files / Upload folder / separator / Trash / Detailed usage. Not added to the `bar` variant.
- Shown only when the current folder has at least one file and selection mode is off (hide it while in selection mode).
- It calls a new page callback `onStartSelection` that sets an explicit state, e.g. `isSelectionModeOn` in DockspaceFilesPage. On phone, `selectionMode = isSelectionModeOn || selectedFilePaths.length > 0` is what FileList receives. On desktop keep `selectedFilePaths.length > 0`.
- After choosing it, the menu closes and focus moves to the selection bar's status text or first checkbox (not lost to body).

### 2. Selection mode on phone (option 2's bar)
- The existing selection bar (`selectionActions`, `.dockspace-browser__selection-bar`) is shown at the top of the list, `position: sticky; top: 0`, even with 0 selected.
  - 0 selected: text "Tap files to select"; **Move** disabled (`disabled`); **Cancel** enabled.
  - N selected: "N file(s) selected" (existing copy), Move enabled, Cancel. Keep the existing `aria-live="polite"` feedback; make the count text polite-live too.
- Every file row shows its checkbox (no hover needed); tapping anywhere on a file row toggles it (existing `onToggleSelection` path). Folder rows are dimmed with the disabled checkbox (existing look) and must not navigate: give the folder button `aria-disabled="true"` and ignore clicks while in selection mode on phone.
- Hidden while in selection mode: the floating Upload button and the parent-folder chips (the uploads progress card stays). Breadcrumb and back button stay.
- Press-and-hold does nothing in selection mode (no menu), same as today's context-menu suppression.
- Leave selection mode (clear selection and `isSelectionModeOn = false`): Cancel; a Move that finishes with no failures (existing behaviour, failed files stay selected and the mode stays on); changing folder (existing effect that clears selection on folder change must also reset the flag); opening the preview is impossible while in the mode. Deselecting the last file does NOT leave the mode on phone (bar returns to "Tap files to select").
- After leaving, taps preview/open again.

### 3. No row `⋯` on phone; press and hold opens the item menu
- In the phone layout, do not render the row `DropdownMenu.Trigger` (`Actions for {name}`) on file or folder rows. Keep the `DropdownMenu` itself (content with the same actions: files Rename, Download, Move to Trash; folders Rename, Download, Move, Move to Trash), opened programmatically and anchored with the existing fixed `menuAnchor` at the press point (clamp so it stays inside the viewport with an 8 px margin; flip up when it would overflow the bottom).
- Long-press detection (a small shared hook, e.g. `useLongPress`, in apps/web/src/hooks): on `pointerdown` with `pointerType` `touch` or `pen` on the row, start a **500 ms** timer. Cancel on `pointerup`, `pointercancel`, `pointerleave`, or movement of more than **10 px** from the start point (so scrolling never opens a menu). When it fires: open that row's menu at the start point, set a "long-press handled" flag, and swallow the click that follows the release (so the preview does not also open). A release before 500 ms is a normal tap: preview the file / open the folder as today.
- Pressed feedback: while the timer runs (after ~150 ms, so quick taps and scrolls do not flash), the row gets a pressed state: `background: rgba(77,168,255,.18)` and `transform: scale(.985)` (no transform under `prefers-reduced-motion: reduce`). Optional `navigator.vibrate?.(10)` when it fires.
- Native behaviour suppressed on phone rows: `-webkit-touch-callout: none; -webkit-user-select: none; user-select: none; -webkit-tap-highlight-color: transparent;` on the row button/li, and `onContextMenu` always calls `preventDefault()` on phone. Android Chrome fires `contextmenu` on long-press: if the long-press hook already opened the menu, ignore it; otherwise open the menu from it (one code path, never two menus). Images in rows must not start a native drag (`draggable={false}` if any).
- Mouse right-click and the keyboard ContextMenu key / Shift+F10 still open the menu in the phone layout (narrow desktop windows): handle `contextmenu` for mouse as today, and add `onKeyDown` on the row button for `ContextMenu` and `Shift+F10` that opens the menu anchored at the row's bottom-left.

### Accessibility
- Each phone row button gets `aria-describedby` pointing at one shared visually hidden element (id e.g. `dockspace-row-actions-hint`): "Press and hold, or press Shift+F10, for more actions." Do not add `aria-haspopup` to the row (its primary action is open/preview).
- When the menu opens (long-press, contextmenu or key), focus moves to the first menu item (existing DropdownMenu behaviour); role `menu` with label "Actions for {name}"; Escape or tapping outside closes it and returns focus to the row button.
- Screen-reader users on iOS/Android reach it with the platform long-press gesture (double-tap and hold), which delivers the same pointer events.
- In selection mode, checkboxes keep `aria-label="Select {name}"`; Move's disabled state uses the native `disabled` attribute; the count is announced politely.
- Touch targets: menu items and bar buttons at least 44 px tall on phone.
- No new serious or critical axe violations (check phone layout in normal mode, selection mode with 0 and 2 selected, and with an item menu open).

### Copy
- Folder options item: "Select items". Bar: "Tap files to select" / "1 file selected" / "N files selected"; buttons "Move", "Cancel". Hidden hint: "Press and hold, or press Shift+F10, for more actions."

### Tests (web)
- Phone (mock matchMedia to match `(max-width: 900px)`): Folder options shows "Select items"; choosing it shows the bar with Move disabled; tapping a file row checks it and does not open the preview; Cancel leaves the mode and a tap opens the preview again; no `Actions for …` buttons are rendered; a 500 ms touch press (fake timers + pointer events) opens the `Actions for {name}` menu and the following click does not open the preview; a press released before 500 ms or moved more than 10 px does not open it; `contextmenu` event is default-prevented; Shift+F10 opens the menu.
- Desktop: existing selection and row menu tests still pass unchanged; "Select items" is absent from Dockspace options.

1. (non-blocking) `isSelectionModeOn` is only cleared on phone paths. If a narrow window enters the mode and is widened past 900 px, and the user clears the selection on desktop, narrowing the window again brings back an empty selection mode. Cancel recovers. A possible follow-up is to reset the flag when `isPhone` turns false.
