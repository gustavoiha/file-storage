# T-0036 Gallery shows a new upload's thumbnail without a reload
Issue: #79
Request: #65
Origin: T-0033
Status: review

## Goal
After T-0033, a file uploaded from the media gallery appears in the gallery right away, but its tile shows the generic placeholder icon instead of its thumbnail until the page is reloaded or the tab regains focus. The single post-batch `GET /media` (T-0033's `useRefreshMediaAfterUploads`, wired through `onBatchComplete` in `useDockspaceUploadDialog`) returns before the asynchronous thumbnail Lambda has written the thumbnail, so the new item has no `thumbnail` and nothing fetches again. Found while testing T-0033 (#74), round 1, finding 1.

Notes: the gallery query is infinite and paged (120 per page), so a plain invalidation re-requests every loaded page. Prefer a targeted, bounded follow-up (for example refetch page 1 or the new items only, a few times with backoff, while recently uploaded image items have no thumbnail). Videos or files that never get a thumbnail must not cause endless polling. T-0030 and T-0034 touch the same gallery files; rebase on main before the PR.

## Acceptance criteria
1. After an upload from the media gallery, the new tile shows its thumbnail within a few seconds of the thumbnail being generated, with no reload or tab switch (desktop and phone).
2. The follow-up is bounded: it runs only while recently uploaded items still have no thumbnail, and stops once they have one or after a time limit.
3. T-0033's behaviour (one gallery refetch per upload batch, not one per file) and the T-0029/T-0031 paging behaviour (one request at a time, status text only near the end) are unchanged.
4. Tests cover the thumbnail follow-up and its stop conditions. Build, typecheck and tests pass.

## Security review (round 1)
PR #89, reviewed at the head of `agent/T-0036-gallery-thumbnail-followup`. Frontend only (`apps/web`): no handler, route, CDK, IAM, S3 or dependency change.

No findings.

- Auth and access: the follow-up only calls the existing `listMedia(dockspaceId, { limit: 120 })` (`GET /media`, same Cognito-authorized route and ownership check the gallery already uses), for the dockspace the page is on. No new endpoint, no ids or user ids added to a request. The uploaded paths stay client-side: they are only matched against items the server returned, never sent.
- Cache writes: `withNewThumbnails` copies only the server's `thumbnail` object onto already-loaded items with the same `fileNodeId` from the same user/dockspace query key (`['media', userId, dockspaceId]`); the follow-up is disposed when the user or dockspace changes, so a late response cannot land in another user's or dockspace's cache. Thumbnail URLs are rendered the same way as before (no new HTML or URL sinks).
- Abuse/limits: bounded to 13 requests (about 55 s) per batch per open gallery, restarted only by a finished upload batch; not a meaningful load on the API.
- Secrets/logging: no tokens, paths or responses logged; failed rounds are swallowed without logging.

## Code review (round 1)
PR #89 at 5304562. Read the full diff, the gallery query, tile rendering, the upload dialog's batch drain and the backend `GET /media` (sorted newest `updatedAt` first, thumbnails only when READY, so page 1 holds the new uploads). Ran the three touched test files locally: 34 tests pass. No conflict with current main (T-0037 touches other files).

What holds up: one gallery refetch per batch is unchanged (the follow-up never invalidates or refetches the infinite query and never touches its fetching state, so paging and the status text are unaffected); the bound is a fixed list of 13 waits (~55 s) that restarts per batch in a single chain (the `run` counter stops an in-flight round from forking a second chain); it skips and drops writes while the gallery query is fetching, and writes only add missing thumbnails by file node id, so the order in which a gallery refetch and a follow-up response land does not matter; dispose on unmount or dockspace change is covered; tiles render straight from `item.thumbnail`, so the copied thumbnail shows. Tests cover arrival, partial arrival, give-up, trashed item, failed request, busy query, restart, in-flight restart and dispose, plus the wired hook (no second invalidation, pages unchanged).

C1 (non-blocking) `apps/web/src/hooks/useMedia.ts` (fetchLatest, `limit: MEDIA_PAGE_SIZE`) and `apps/web/src/lib/mediaThumbnailFollowUp.ts` `pathsAwaitingThumbnail` / `scheduleNextRound`: a batch larger than one page (more than 120 uploads, e.g. a camera-roll dump) is only partly followed. Uploads 121+ are not on the first page that the follow-up fetches, so when they are loaded (the user had 2+ pages loaded) the follow-up never finds their thumbnails and runs its full ~55 s for nothing. And paths not loaded when the batch refresh lands are dropped from the followed set on the first recompute, so tiles that the user then scrolls into (fetchNextPage before their thumbnails exist) keep the placeholder until a focus refetch or reload. Criteria 1-2 hold for the common case (batches up to 120); the large-batch case misses criterion 1. Fix if wanted: size the follow-up request to the followed count (up to the backend's 200 max), and keep not-yet-loaded paths in the followed set (only dropping a path once its item is loaded with a thumbnail or the bound ends), so tiles loaded later in the window are filled too. Or accept it as a known limit and note it on the issue.

No blocking findings.
